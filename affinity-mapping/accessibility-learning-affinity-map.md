# Accessibility Learning Affinity Map

**Artifact type:** Portfolio Simulation

## Raw Observations

- Teams often know accessibility matters but do not know where to start.
- Automated tools are treated as final answers instead of partial signals.
- Developers want code examples tied to specific accessibility failures.
- Designers want earlier guidance on focus order, labels, and content structure.
- Users with accessibility needs care about predictability, control, and recovery.
- Compliance language can feel abstract without user impact examples.
- Teams struggle to prioritize issues when severity and effort are mixed together.

## Grouped Themes

| Theme | Supporting Observations |
| --- | --- |
| From compliance to impact | Users need plain-language explanations of who is affected and how. |
| Role clarity | Designers, developers, QA, and product owners need different entry points. |
| Prioritization | Teams need separate views of severity, frequency, and remediation effort. |
| Learning by doing | Interactive audits help users connect rules to product behavior. |
| Inclusive validation | Automated checks must be paired with keyboard and assistive technology review. |

## User Pain Points

- Accessibility issues are discovered too late.
- Guidance can be technical without explaining product impact.
- Teams are unsure which issues block release.
- Remediation examples are not always tied to real UI states.

## User Needs

- Role-specific checklists
- Severity guidance based on user impact
- Examples of good and poor implementations
- Support for keyboard, screen reader, and cognitive accessibility checks

## Opportunity Areas

- Translate WCAG criteria into task-level product guidance.
- Provide issue templates that include impact, evidence, and next action.
- Add lightweight accessibility checkpoints to design and development workflows.
- Create learning paths for different roles.

## Product Recommendations

- Build an audit workflow that separates detection, impact, priority, and remediation.
- Include assistive technology notes in examples.
- Use plain language summaries before technical details.
- Add "test this yourself" steps for keyboard and screen reader checks.

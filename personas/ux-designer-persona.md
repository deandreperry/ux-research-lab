# Provisional UX Designer Archetype

- **Status:** Hypothesis archetype; not validated participant segmentation

## Intended Use

Use this archetype to surface assumptions about pattern decisions and handoff. It does not represent every designer and should not be used as participant evidence.

## Background

A practitioner who defines complex web workflows, prototypes interactions, and aligns product intent with engineering constraints. The relevant behavior is how evidence and collaboration shape pattern decisions—not a fictional identity.

## Goals

- Choose patterns that are usable, accessible, and technically realistic.
- Explain design decisions with clear rationale.
- Reduce rework during handoff.
- Build confidence that designs meet user needs before implementation.

## Needs

- Pattern examples with usage guidance and accessibility notes
- Research summaries that connect user behavior to design choices
- Clear documentation for edge cases and interaction states
- Early engineering feedback on feasibility

## Pain Points

- Component documentation often omits context and tradeoffs.
- Accessibility guidance can appear late in the process.
- Product deadlines can compress research and validation.
- Handoff can lose intent when specs focus only on visuals.

## Behaviors

- Searches design systems and competitor products for examples.
- Uses prototypes to align stakeholders.
- Asks engineers about constraints before finalizing flows.
- Keeps notes on recurring usability issues.

## Tools Used

Figma, FigJam, design systems, product analytics dashboards, accessibility checklists, issue trackers, and documentation sites.

## Accessibility Considerations

Maya needs reminders and examples for keyboard flow, focus states, labels, error messaging, content hierarchy, and reduced-motion alternatives.

## Product Opportunities

- Add designer-focused pattern guidance with interaction rationale.
- Provide accessibility prompts during early exploration.
- Include handoff notes that describe behavior, not just layout.

## Jobs To Be Done

When choosing a UI pattern, this practitioner needs credible rationale, states, accessibility behavior, and feasibility context so they can defend a decision and reduce downstream ambiguity.

## Validation Requirements

Validate the assumed behaviors through recent examples and observed evaluation tasks. Link claims to evidence, retain designers who work differently, and segment by behavior or responsibility when the data supports it.
